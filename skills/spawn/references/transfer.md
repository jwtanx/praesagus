# Verified role transfer

## Inventory and checkpoint

1. Resolve requested roles from agent-operations/roles.json. A single-role request uses the current calling chat as destination; verify its ID from app context/tool evidence rather than guessing from a title. Keep its ID distinct from the source. Read the private registry afresh because another chat may already have completed a transfer. If destination equals the active registered source, perform idempotent onboarding/reconciliation only: no new chat, source retirement or schedule duplication. If another destination already holds the role and the user correction is ambiguous, confirm whether to keep it or adopt the calling chat before moving ownership again. Inspect list_threads, the private active-role registry and read_thread as needed; verify project, role, host and actual predecessor IDs. Do not assume the executing chat is Lead. Use list_archived_threads if resuming an incomplete transfer. Multiple matching candidates require human clarification. No predecessor is a fresh bootstrap: do not invent a prior context or archive target.
2. For first Trader adoption, identify Consultant as the financial predecessor and the separately verified Researcher-owned daily-report schedule as a legacy transfer dependency. Capture both relevant checkpoints; do not archive Researcher until all its active assignments and schedules have an accepted destination. General research ownership moves to Lead/Engineer as appropriate, never blindly to Trader. `/spawn all` includes retirement of these legacy roles only after verified handoff of every outstanding responsibility. Record unresolved retirement blockers explicitly.
3. Inspect compact collaborator status. Request a bounded checkpoint from busy predecessors under the invocation's message authorization; wait for a safe completion/idle boundary. Do not forcibly interrupt, archive or duplicate their work. If unavailable, retain source and record pending transfer. An idle source's read_thread summary must be cross-checked against canonical specs, private state and Git; ask a checkpoint only where needed.
4. Use agent-operations/handoffs templates (and records.md field contract) to save a private transfer receipt under lead-state/transfers/ with unique transaction ID, MYT date, requested roles, source IDs, exact phases and settings, objective, human-selected direction, permissions, ticket/check evidence, source versus verified findings, HEAD, dirty-file ownership, pending reviews, next steps, private checkpoint paths and schedule inventory. Use normal file tools; avoid secrets in messages/logs. Read back before any destructive schedule mutation. Back up full settings, statuses, notification preferences and future one-time anchors/checksums. Do not overwrite older unfinished transfers or backups.

## Held bootstrap

5. For a single role, adopt the current calling chat; never use create_thread or fork_thread. Read the actual startup prompt and reviewed compact checkpoint into the current agent's working context. Verify local checkout/project association; a projectless calling chat can retain its current projectless identity while using the verified repository cwd. Rename the destination with set_thread_title (omit threadId to target the caller where supported) only after source/destination identity is established; record returned evidence/IDs. Keep it held against normal work until cutover. For all, resolve existing human-started destination chats and an explicit role map; do not guess which current chat should take a role or create missing destinations without an explicit new-chat request. Reuse verified destinations on retries. A separately authorized creation follows list_projects/create_thread and ready-ID rules; pending clientThreadId is never a usable threadId. Trader model requirements are not a reason to create a duplicate: use supported settings controls or disclose required human model adjustment.
6. For the calling destination, actually read startup/checkpoint, record self-readiness (role, held state, accepted pending ownership, gaps) in the receipt and acknowledge in commentary; do not send a message to yourself or wait_threads on your own active turn. For other destinations use checkpoint/bootstrap messages and bounded waits <=60 seconds for real acknowledgments. For all obtain the full peer map/readiness before cutover. A title change alone is not readiness. If acknowledgment fails, preserve source and held destinations; do not claim takeover.

## Schedule cutover

7. View each actual automation configuration and verify exact source target_thread_id. Inspect local metadata where available. Register schedule ownership per role; Engineer normally has none. Unknown other-chat recovery entries remain untouched and reported. A schedule backup with removed entries must be reconciled too; its original ownership must be verified before rebinding it to a successor. Preserve integrity/progress and original pause reasons; never restore expired one-time wakes.
8. Pause verified predecessor recurring schedules, recording each mutation/readback; preserve original statuses. Coordinate in-flight scheduled runs to a safe idle boundary before replacement. Prepare equivalent successor schedules inactive with the automation tool; correct legacy daily-report cadence to 08:00 and role references to the verified new map. Preserve notification policy and other unrelated settings. Prefer supported in-place target reassignment while paused if the tool accepts it; otherwise create verified inactive replacements. Do not assume unsupported update fields work. Record every new ID before the next mutation.
9. Verify successor target, complete prompt/configuration, timezone/cadence/status and supported exact anchors. Only then delete superseded predecessor schedules through the tool and verify absence. With in-place reassignment verify no schedule remains attached to the predecessor. If deletion/update/readback fails keep successors inactive and stop dependent cutover. Product confirmation remains pending until confirmed; no workaround schedule. Conditional recovery follows agent-operations/schedules/resource-recovery.md, not a recurring 18:05 timer.
10. Run fresh battery/usage checks before any Lead activation. Safety guards or human-paused status win: migrate schedules paused or preserve removed-backup state. Transfer surviving eligible future one-time wakes only when exact scheduling is supported; expired wakes are skipped. Record activation eligibility only for replacements whose original status was ACTIVE and whose resource/time guards permit; keep every successor schedule PAUSED through retirement and release acknowledgment. Activation happens in step13, not here. Check actual tool result/readback; do not infer success from file changes. During partial failure, retain checkpoint and receipt, reconcile actual state before retry; never blindly roll back by activating both source and successor schedules.

## Accept and retire

11. Write verified successor role/host/project IDs and schedule map to private registry and private Lead context. Rebind existing saved-backup ownership only with recorded source-to-successor evidence; preserve paused states, entry history and checksum. Update peer mappings for both replaced and surviving roles through authorized messages. Role and schedule mutation authority now follows this verified registry, replacing old hardcoded Lead restrictions.
12. For `all`, first require the group readiness/cutover condition in step13; partial failure keeps all requested predecessors intact. Before retiring any source, durably record `accepted-held` successor ownership and `retired-source` status with the exact next release step in the private receipt; read back. On a crash between retirement and release, verify that receipt, successor readiness and schedules, then release that existing successor without recreating a chat or restarting the retired source. Confirm all accepted responsibilities, safe resource state (or recorded paused state), successor acknowledgments and schedule uniqueness. Rename each eligible idle predecessor to `Role [YYYY-MM-DD]` using set_thread_title, then archive with set_thread_archived. If dates collide the IDs in receipt disambiguate. A failed archive leaves it marked retired/idle and must not restart work. Never archive an unrelated current chat. The calling destination must never be archived by its own takeover. If source equals the caller, this is onboarding/reconciliation, not replacement: skip retirement entirely.
13. For `all`, do not retire any requested predecessor or release any successor until every requested role is ready and the complete group schedule cutover is verified (safe paused state counts as ready; pending confirmation does not). Legacy Researcher retirement can remain pending if an unrelated assignment is not yet transferable, but that assignment must have a recorded continuing owner and must not overlap successor work. Release verified successors with their final peer/schedule map and exact next authorized step; Lead initiates coordination, Trader resumes finance/report responsibility, Engineer resumes accepted coding. A role with an unresolved takeover remains held. For all, release Engineer/Trader then Lead after the group map and schedules are coherent. For the calling destination, record actual self-release acceptance in the private receipt after verified cutover; do not wait on yourself. Obtain other destinations' actual release acknowledgments via bounded wait_threads before activating eligible successor schedules. Then activate/read back only originally ACTIVE schedules with fresh safe resources, correct target and time guards; preserve original PAUSED status. Scheduled prompts must consult the private role/transaction state and exit while held or retired. Pending product confirmation or failed release acknowledgment keeps schedules paused; record partial transfer without claiming active continuation. Paused resources or lack of human direction mean acknowledge waiting state, not invent work. Report adopted destination IDs, renamed/archived sources, transferred/paused/skipped schedules and remaining blockers.

## Replay cases (offline; no live mutation)

- Busy Engineer writing ticket files: checkpoint/wait, no overlapping implementation, no forced archive.
- Two plausible Lead chats: identity question, no mutation.
- New Trader acknowledges; report replacement pending product confirmation: source retained, replacement held, no successful-transfer claim.
- Source schedule PAUSED: replacement PAUSED, no startup reactivation.
- Crash after destination rename: receipt + tool inventory reuse the same human-started chat; no creation or duplicate.
- Old schedule deletion fails: replacement stays inactive; source not archived.
- Battery 8% or unknown weekly window during all: checkpoint, no Lead activation; verified migration can remain held/paused.
- Legacy Consultant idle but Researcher has another live assignment: Trader takeover can finish for accepted finance/report responsibility; Researcher retirement remains pending, no blanket archive.
- `/spawn all` with one failed bootstrap: no group release, preserve sources and partial receipt.
- No predecessor: adopt current chat held as a fresh role; no fabricated context, inherited permissions or archive target.
- Single-role current chat already registered as that role: reconcile context/schedules; no create, fork or archive.
- Another Lead already completed takeover while the human corrects behavior: clarify keep-versus-adopt before a second transfer; update instructions independently.
- All has only one destination chat: request the missing destination map, no silent creation.
