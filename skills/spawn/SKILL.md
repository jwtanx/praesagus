# Adopt a replacement role

Resolve this SKILL.md to its canonical filesystem location before interpreting relative references when discovered through a symlink.

Read [agent operations](../../agent-operations/README.md), [role configuration](../../agent-operations/roles.json) and [transfer procedure](references/transfer.md). Use [handoff templates](../../agent-operations/handoffs/README.md) for private records. Accept lead, trader, engineer, ai-engineer or all. `ai-engineer`, `ai_engineer` and `ai engineer` resolve to canonical `AI Engineer`, case-insensitively; `engineer` remains canonical `Engineer`. Resolve only exact normalized configured names; ambiguous abbreviations or combined role requests need clarification. The read-only [role selector](scripts/resolve_role.py) accepts `python3 skills/spawn/scripts/resolve_role.py ai-engineer` (or `all`) and returns configured canonical roles and destination mode; it performs no app, registry or schedule mutation. `all` means every role in roles.json, not every chat in the app. `$spawn` is native skill invocation; `/spawn` is a natural-language alias, not a custom command registration.

A normal single-role invocation adopts the current calling chat as the successor; it does not authorize creating another chat. An explicit human request for a fresh role chat instead authorizes one new local destination for that role: the caller coordinates and never becomes the successor. The selector's `--fresh` flag only describes this explicit mode; it cannot supply missing authorization. The human's invocation authorizes reading/applying the selected startup prompt and compact checkpoint, renaming the verified destination to the role, project-scoped checkpoint/bootstrap/release messages, moving their verified role schedules, renaming predecessors to `Role [YYYY-MM-DD]` (MYT replacement date) and archiving them after verified takeover. It does not authorize a live replacement merely because this skill is being authored/reviewed. Preserve unrelated chats, worktrees, schedules and human pauses. If multiple predecessors match or ownership is ambiguous, ask for identity rather than guess.

Use the current chat with a summarized checkpoint plus the actual startup prompt; do not call create_thread or fork_thread for a normal single-role invocation. Resolve the predecessor separately and never retire the current destination. If source and destination are already the same registered role, reconcile/read the context and schedules without another transfer or archive. Apply the human-authorized requested defaults from agent-operations/roles.json on supported fresh creation/dispatch; distinguish requested and observed settings. Adoption does not itself change the caller runtime. An unavailable preference must not block useful work; preserve an available supported setting and never claim it independently verified. Do not create another Trader to force a model override.

For `all`, the invocation explicitly authorizes creating one fresh local chat per configured role with create_thread and renaming each to its exact configured role name (currently Lead, Trader, Engineer and AI Engineer). Call list_projects first and select the verified Praesagus project; use its local environment without a worktree or fork. The calling chat coordinates the transfer and does not adopt a role. Do not ask for a destination map or separate creation confirmation. Record each returned ID before creating the next chat; on retry reuse this transaction’s verified destinations instead of creating duplicates. Read the current registry first to avoid replacing a takeover completed in another chat. If the human explicitly supplies destinations instead, honor that map.

When the human says not to pull over context, do not read predecessor chat history or private narrative checkpoints and do not request narrative handoffs. Bootstrap each role from its actual startup prompt, the human-supplied progress summary and canonical ticket evidence. Still verify predecessor identity, idle status, dirty-file ownership and schedule configuration through bounded operational evidence; if that cannot be established without excluded context, keep the affected transfer held and report the gap.

For an explicitly requested fresh single-role chat, follow the same verified project/creation/held-readiness/cutover/release procedure as `all`, restricted to that requested role; do not replace peers or guess a predecessor. Reuse returned destination IDs on retry and emit a created-thread directive for every actual creation.

AI Engineer owns datasets, model training, calibration, artifacts, inference/evaluation and sentiment modeling; Engineer supplies supporting infrastructure; Trader reviews financial meaning and research decisions; Lead accepts scope and integration. Reuse [the AI Engineer skill](../ai-engineer/SKILL.md) for model work. Engineer and AI Engineer have no default schedules; inspect actual ownership before concluding that none exist. Preserve historical owners and unrelated roles such as Designer. Adding configuration or editing this skill does not create a role or autonomous runtime.

When the caller is the successor, it records its own held readiness and release acknowledgment after actually reading the startup/checkpoint; do not message or wait on yourself. Other destination chats acknowledge via authorized messages and bounded wait_threads. Never archive a busy predecessor or activate overlapping schedules. A tool failure or pending confirmation stops dependent mutations; preserve a private transaction receipt for retry. Report partial progress accurately. Emit a created-thread directive for every chat actually created by `all` or an explicit fresh-role request; use clientThreadId only while creation is pending. This skill is an agent procedure, not atomic migration code or a guarantee of background execution.
